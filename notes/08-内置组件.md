# 内置组件:React 自带的四个"特殊标签"

> 📌 本文的 React 技术知识,来自 D 盘的 **DeepSeekMonitorWindows-1** 项目。

06 篇梳理了官方参考里的**内置 Hook**(`useXxx` 那批函数);同一个参考页还有另一栏——**内置组件**。先搞清楚你在 JSX 里写的标签到底分三类:

| 标签写法 | React 怎么处理 | 例子 |
|---|---|---|
| 小写开头 | 当作浏览器 DOM 元素,渲染成真实节点 | `<div>`、`<button>` |
| 大写开头(你定义的) | 当作组件变量,执行你写的函数 | `<MyButton>` |
| 大写开头(React 自带) | **内置组件**:有特殊行为,不是普通 DOM | `<Fragment>`、`<Suspense>` |

其实 07 篇已经用过内置组件了——`MyApp` 返回值里那对 `<>...</>`,就是 `<Fragment>` 的语法糖(03 篇的翻译规则:`<>...</>` 编译后就是 `jsx(Fragment, …)`,`<div>` 编译后是 `jsx('div', …)`)。

官方参考(<https://zh-hans.react.dev/reference/react/components>)只登记了四个:

| 内置组件 | 一句话 | 什么时候用 |
|---|---|---|
| `<Fragment>`(可写 `<>`) | 给元素分组,不留 DOM 节点 | 组件要返回多个并列元素 |
| `<Profiler>` | 测量子树每次渲染的耗时 | 查性能瓶颈 |
| `<StrictMode>` | 开发期把可疑代码"双跑"暴露问题 | 挂在根部,只影响开发 |
| `<Suspense>` | 子组件没就绪时先显示 fallback | 懒加载、慢数据 |

下面逐个过,每个都配完整可跑的示例 + 逻辑链路。

## `<Fragment>` / `<>...</>`:隐形的分组

JSX 里一堆并列的元素必须有一个父级包着(JSX 是表达式,只能有一个根)。拿 `<div>` 包会**真实创建一个 DOM 节点**——多数时候无所谓,但表格这种对结构敏感的地方会直接坏掉:`<tr>` 里只允许放 `<td>`/`<th>`,塞个 `<div>` 浏览器不认。

`<Fragment>` 就是"包了但没包"的分组:JSX 层面有个父级,DOM 层面零痕迹。

```jsx
import { Fragment, useState } from 'react';

function ScoreCells({ items }) {
  // 返回「一串 <td>」:列表的 key 必须写在 <Fragment> 上
  // (短语法 <> 不能带任何 props,包括 key)
  return items.map((item) => (
    <Fragment key={item.name}>
      <td>{item.name}</td>
      <td>{item.score}</td>
    </Fragment>
  ));
}

function ScoreTable() {
  const [items, setItems] = useState([
    { name: 'React', score: 98 },
    { name: 'Vue', score: 95 },
    { name: 'Svelte', score: 92 },
  ]);

  return (
    <div>
      <table border="1">
        <tbody>
          <tr>
            {/* 组件返回 3 组 Fragment、共 6 个 <td>,全部平铺进这一个 <tr> */}
            <ScoreCells items={items} />
          </tr>
        </tbody>
      </table>
      <button onClick={() => setItems([...items, { name: 'Angular', score: 90 }])}>
        加一门课
      </button>
    </div>
  );
}

export default ScoreTable;
```

逻辑链路:

- ① `ScoreTable` 渲染 → `<tr>` 里遇到 `<ScoreCells/>` → 执行它,得到 3 个 `<Fragment>`,每个里面 2 个 `<td>`;
- ② React 把 Fragment **拆开平铺**,`<tr>` 最终直接收到 6 个 `<td>`——中间没有任何包装节点,F12 看不到 Fragment 的影子;
- ③ 点「加一门课」→ `setItems` → 重渲染 → 数组多一项,新的 `<Fragment key="Angular">` 连同 2 个 `<td>` 插进 `<tr>`。

两种写法的取舍:

- `<>...</>`:短语法,最常用,但**不能带任何 props**;
- `<Fragment key={...}>`:完整写法,唯一多出来的本事是能带 `key`——所以**在 `.map()` 列表里分组时必须用它**(07 篇讲过列表要 key,短语法给不了)。

## `<Profiler>`:给子树计时

包裹任意子树,每次这棵子树**完成一次提交**,React 就调用一次你传的 `onRender`,把这次渲染的耗时数据递给你。

```jsx
import { Profiler, useState } from 'react';

function fib(n) {
  return n < 2 ? n : fib(n - 1) + fib(n - 2);
}

function Counter({ heavy }) {
  const [count, setCount] = useState(0);
  // 每次渲染都重算一遍 fib,模拟「昂贵渲染」(仅演示,别学它)
  const dust = heavy ? fib(31) : 0;

  return (
    <button onClick={() => setCount(count + 1)}>
      count = {count}{heavy ? '(每次渲染算 fib(31)=' + dust + ')' : ''}
    </button>
  );
}

export default function App() {
  const [heavy, setHeavy] = useState(false);

  // 每当 <Profiler> 包住的子树完成一次提交,React 就调用一次它
  function handleRender(id, phase, actualDuration, baseDuration) {
    console.log(`[${id}] ${phase}:实际 ${actualDuration.toFixed(2)}ms / 基线 ${baseDuration.toFixed(2)}ms`);
  }

  return (
    <div>
      <label>
        <input
          type="checkbox"
          checked={heavy}
          onChange={(e) => setHeavy(e.target.checked)}
        />
        开启昂贵计算
      </label>
      <Profiler id="计数器" onRender={handleRender}>
        <Counter heavy={heavy} />
      </Profiler>
    </div>
  );
}
```

逻辑链路:

- ① 首次渲染 → 子树提交 → `onRender(id, 'mount', …)` 打出挂载耗时;
- ② 点 `+1` → `setCount` → 只有 Profiler 包住的这棵子树重渲染 → `onRender(id, 'update', …)`,`actualDuration` 平时零点几毫秒;
- ③ 勾上「昂贵计算」→ 之后每次渲染都要算 `fib(31)` → update 的 `actualDuration` 跳到十几毫秒——瓶颈就这样被定位到"这棵子树的渲染"上,再逐层缩小 Profiler 的范围就能揪出元凶。

`onRender` 六个参数,前四个最常用:

| 参数 | 含义 |
|---|---|
| `id` | 你在 `<Profiler id=…>` 上起的标识,嵌套多个时用来区分是谁 |
| `phase` | `'mount'`(首次)/ `'update'`(更新) |
| `actualDuration` | 本次提交渲染这棵子树的实际耗时(ms) |
| `baseDuration` | 不考虑 memo 优化时,整棵子树最近一次渲染的估计耗时(ms) |
| `startTime` / `commitTime` | 本次渲染开始/提交的时间戳,算时间线用 |

三个注意:**生产构建的 React 里 `onRender` 不会触发**(测量本身有开销,别带到线上);它只读不写,不影响渲染结果;粒度由你决定,可以整页套一个粗看,再缩小范围细查。

## `<StrictMode>`:开发期的"找茬模式"

不改变任何行为、不渲染任何 DOM,只在你跑**开发构建**时把可疑代码"双跑"一遍,让问题自己暴露:组件函数每次渲染被调用两遍、`useState` 初始化函数跑两遍、Effect 挂载→清理→再挂载。

```jsx
import { StrictMode, useEffect, useState } from 'react';

let renderCount = 0;

function Probe() {
  renderCount += 1; // 在渲染函数里改外部变量——不纯!StrictMode 专门抓这种
  console.log(`渲染第 ${renderCount} 次`);

  const [count, setCount] = useState(() => {
    console.log('useState 初始化函数执行');
    return 0;
  });

  useEffect(() => {
    console.log('Effect 挂载(模拟订阅)');
    return () => {
      console.log('Effect 清理(模拟退订)'); // 漏写清理函数,StrictMode 下立刻穿帮
    };
  }, []);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

export default function App() {
  return (
    <StrictMode>
      <Probe />
    </StrictMode>
  );
}
```

逻辑链路(开发构建的控制台预期):

```
渲染第 1 次 → useState 初始化函数执行 → 渲染第 2 次 → useState 初始化函数执行   ← 组件函数和初始化都双跑
Effect 挂载 → Effect 清理 → Effect 挂载                                          ← Effect 一出生就演习一次「卸载再重挂」
点一次按钮:渲染第 3 次、渲染第 4 次                                               ← 每次更新也是双跑
```

为什么这么设计:React 要求渲染函数是**纯函数**(同输入同输出、不碰外部)。双跑一遍,任何副作用都会重复出现——日志打两遍、外部变量加两次——一眼识破。Effect 的「挂载→清理→再挂载」则是演习将来真会发生的卸载重挂(如 Fast Refresh、组件被移出又移回屏),提醒你**清理函数必须写对**:如果挂载时订阅了却在清理函数里忘退订,这里会重复订阅,当场穿帮。

两个注意:**生产构建里 StrictMode 零行为**,一行都不会多,所以放心挂在根部;它只在开发构建里"吵",所以看到双份日志不是 bug,是它在工作。

## `<Suspense>`:等子组件时先顶班

包住一棵子树,当子树里有组件**声明了"我还没就绪"**(挂起,suspend)时,Suspense 就把整棵子树的位置换成 `fallback` 先顶班;就绪后自动换回真内容。最经典的搭档是 `lazy` 懒加载:

```jsx
import { Suspense, lazy, useState } from 'react';

// 懒加载组件:首次渲染到它时才真正 import,加载完之前它「没就绪」
const MarkdownPreview = lazy(() => import('./MarkdownPreview.js'));

export default function DocPage() {
  const [showPreview, setShowPreview] = useState(false);

  return (
    <div>
      <button onClick={() => setShowPreview(true)}>显示预览</button>
      {showPreview && (
        <Suspense fallback={<p>⏳ 正在加载预览组件……</p>}>
          <MarkdownPreview />
        </Suspense>
      )}
    </div>
  );
}
```

逻辑链路:

- ① 点「显示预览」→ `setShowPreview(true)` → 重渲染,首次遇到 `<MarkdownPreview/>`;
- ② 它的模块还没加载完,组件「挂起」——向上抛出"我没就绪"的信号;
- ③ 离它最近的 `<Suspense>` 接住:把整棵子树的位置**整体换成** `fallback`(替换,不是叠加);
- ④ `import()` 完成、Promise resolve → React 重试渲染子树 → 真组件出现,fallback 消失。用户全程只看到"加载中 → 内容",不用你手写任何 `isLoading` state。

一个关键澄清:「挂起」不是自动的——只有声明过会挂起的东西才会触发 Suspense:`React.lazy` 的组件、支持 Suspense 的数据获取(React 19 的 `use(promise)`、各类数据库)。普通的 `setTimeout` 慢、自己写的 `fetch` 慢,不会让 Suspense 显示 fallback,那还是 `useState` + 手动 loading 的活儿。

## 收个尾:四个组件的分工

- `<Fragment>`:**结构**问题——要分组、又不能多节点(表格、flex 布局);
- `<Profiler>`:**性能**问题——哪里渲染慢;
- `<StrictMode>`:**质量**问题——不纯代码、漏写的清理,开发期双跑暴露;
- `<Suspense>`:**加载态**问题——子树没就绪时的顶班 UI。

前两个纯工具人,该用就用;StrictMode 挂根部常驻;Suspense 配 lazy 按需上。

## 实测验证(2026-09-15,react-val-study/react-built-in-components-demo.html)

四张卡片对照,带时间戳日志实测:

- **🧩 Fragment**:两行按钮对照——`<>` 分组的一行,DOM 里 3 个 button 直接躺在容器里;`<div>` 分组的一行多出一层节点,点「数一数真实 DOM」即时核对。
- **⏱️ Profiler**:计数器包在 Profiler 里,`onRender` 日志打出 phase 与耗时;开关「昂贵计算」(fib(31))前后对比 update 的 `actualDuration`,瓶颈立现。
- **🚨 StrictMode**:同一个 Probe 分别在 StrictMode / 普通模式下挂载(日志带实例编号)——前者渲染、`useState` 初始化日志全部双份,Effect 演习一遍「挂载→清理→再挂载」;后者渲染、初始化单份,Effect 只挂载一次(日志里那条「清理」来自上一个实例的卸载,换模式必然重挂)。点内部 +1 还能看到 StrictMode 下每次更新也渲染两遍。
- **💤 Suspense**:点击创建一个 2 秒后才 resolve 的 `lazy` 组件,亲见 fallback 顶班 2 秒后被真组件**整体替换**;每轮都是新的 lazy,可反复体验。

⚠️ 验证页这次特意用 **development 构建**的 React(之前几页是 production):StrictMode 的双跑、Profiler 的 `onRender` 都只在开发构建里生效——这本身就是本篇的知识点,拿 production 构建去测它俩,只会得到"全是哑的"。

## 记忆口诀

> **分组用 `<>`,计时包 Profiler;开发套 StrictMode,懒加载配 Suspense。**
> Fragment 不留痕,Profiler 只计时(生产不触发),StrictMode 专找茬(仅开发双跑),Suspense 会顶班(就绪后整体替换)。
